Zoventro: Production Readiness, Security & Code Quality Audit

Repository /opt/homebrew/var/www/p at commit 6f9ca68 (main) · Audit date 18 Oct 2026 · Scope: Laravel admin, Node/Express API (apis/), React frontend (frontend/), MySQL schema, configuration, dependencies.
This is a review only; no code was changed. Secret values are never shown here, only where they are.

Verdict: NO-GO for production

The payment code is careful and SQL is parameterised throughout, but authentication is effectively absent on the public side of the product:

  • Every OTP is hard-coded to 123456, in both the Node API and the older Laravel /api. Anyone who knows an organizer's email can sign in as them.
  • Players have no credential. Every game action and the private role screen trust a participant_id integer sent by the client. Any player can read the culprit's secret role and act as any other player.
  • Production secrets and two SSH private keys are in the pushed GitHub history (origin/main), and the current local secrets are the same values.
  • Any organizer account can rewrite or delete the global Cook & Create game content, and an unauthenticated socket event returns the names and emails of any booking's participants.

Fixing the 6 Critical and 10 High items (Phase 0 and Phase 1 below) is the minimum before real users or real payments.

1. Executive summary

Architecture. A Laravel 11 app holds the AdminLTE admin (routes/admin.php) plus a legacy JSON API (routes/api.php). A Node/Express + Socket.IO TypeScript service (apis/, port 6001) runs both games, organizer accounts and Razorpay checkout. A TanStack/React SPA (frontend/) is built to static files. The production nginx layout in setupserver.html (step 9) sends /v1 and /socket.io to Node, sends /admin, /api and *.php to Laravel's public/, and serves the SPA for everything else.

Top risks, in order:

  1. Organizer account takeover via the fixed OTP: C1 and C2.
  2. Leaked credentials in git history: C3. Rotate everything, even if the repository is private.
  3. No player authentication, so game state and other players' secret roles are open: C4, H1.
  4. Privilege gaps: organizers can edit global content (C5), and admin RBAC is mostly unenforced (H4).
  5. PII leaks to unauthenticated callers: C6 and H2.
  6. Unpaid activation: an anonymous caller can complete someone else's booking as cash-on-delivery (COD), which activates it at once (H3).

Overall code quality is uneven. Recent modules are well written, with comments explaining the reasoning, locking and Form Requests (payments, Music Manager, invoice). Older layers carry debug leftovers (echo …; die; handlers, commented-out permission checks, TEMP OTP code), schema changes made at runtime from Node, about 96 MB of unused assets, and 23 TypeScript errors in the frontend.

3. Secrets & configuration

C3 Credentials and private keys in pushed git history

git branch -r --contains confirms both commits are on origin/main (github.com:weamitgiri/amgo).

  • 196407d (Initial commit) added .env (APP_KEY, DB password, mail password, JWT secret, Razorpay test and live secrets) and frontend/.env.
  • b1db283 added the OpenSSH private keys amigo and clear (plus their .pub files). production.txt (deployment notes mentioning DB passwords, AWS keys and tokens) was also tracked.
  • c7322d2 deleted them from the tree but not from history.
  • Comparing hashes (values not printed): the current local APP_KEY, DB_PASSWORD, MAIL_PASSWORD and JWT_SECRET (both apps) are identical to the historic ones.

A leaked APP_KEY lets an attacker forge encrypted values (e.g. the decrypt($id) ids used by admin forms) and, with a session/cookie driver, sessions. A leaked JWT_SECRET lets them mint organizer tokens directly.

Fix
Treat every value as compromised. Rotate APP_KEY, DB and mail passwords, JWT secret and both Razorpay key pairs (and the webhook secret). Revoke both SSH keys on every server and GitHub. Purge history with git filter-repo and force-push only after coordinating. Then move amigo, clear and production.txt out of the repo directory entirely. Add a pre-commit secret scanner (gitleaks).

H10 Repo root is web-served in the local layout

Local Apache serves the parent folder, and the repo-root index.php/.htaccess only rewrite non-existent files. Measured with curl on localhost: /p/.env 200, /p/apis/.env 200, /p/production.txt 200, /p/.git/config 200, /p/vendor/composer/installed.json 200. The private keys returned 403 (permissions 600). The documented production nginx uses public/ as the Laravel root, which is safe, but the live server was not inspected (out of scope).

Fix
On live, confirm that curl https://<host>/.env and /apis/.env return 404. Delete the root index.php/.htaccess shim or add Require all denied for dotfiles, *.txt, *.md, vendor/, storage/ and apis/.

M6 Development defaults in the env files

.env: APP_ENV=local, APP_DEBUG=true, LOG_LEVEL=debug, SESSION_SECURE_COOKIE=false, SESSION_ENCRYPT=false. apis/.env: NODE_ENV=development, which also turns off the OTP rate limiter (H7) and leaks stacks (H9).

Fix
Production env must set APP_ENV=production, APP_DEBUG=false, LOG_LEVEL=warning, SESSION_SECURE_COOKIE=true, NODE_ENV=production, and swap morgan('dev') for 'combined'. Fail API startup if NODE_ENV is unset.

4. Authentication, OTP & sessions

C1 Hard-coded OTP in the Node API

generateNumericOtp() returns '123456' before the CSPRNG code (apis/src/utils/otp.ts:18-19, "TEMP … revert before production"). It is used for organizer registration (organizerController.ts:42), login (:87), resend (:269) and player join (participantController.ts:134). verifyLoginOtp (:120) then issues a 24-hour JWT. The compiled dist has the same code, so a rebuild changes nothing.

Impact: POST /v1/organizer/login {email} then POST /v1/organizer/verify-login {email, otp:"123456"} gives full access to any organizer: bookings, invoices, billing/GST data, results, account deletion.

Fix
Delete the early return. Store a hash of the OTP (not plaintext), compare it with timingSafeEqual, add a per-account failed-attempt counter and lock (5 tries), and invalidate the OTP after the first verify attempt that exceeds the limit. Add a test asserting two calls return different codes.

C2 Legacy Laravel OTP API

routes/api.php exposes /api/v1/auth/login/{send,verify,resend}-otp and /api/v1/game-join/*, all with OTP '123456' (AuthController.php:32,111, GameJoinController.php:97). A successful verify returns the whole Organizer model (:85) and sets status='active' and is_email_verified=true, which can re-activate an account an admin suspended. It writes to the same organizers.otp column the Node API reads, so even after C1 is fixed, an attacker can call Laravel send-otp to plant 123456 and then verify through Node. The production nginx forwards /api to Laravel (setupserver.html:304). Confirmed reachable locally (POST /p/api/v1/auth/login/send-otp → 422 validation).

Fix
The frontend uses Node, so remove routes/api.php registration in bootstrap/app.php:28 and drop api from the nginx location regex. If any part is still needed, port it to Node.

H7 Brute-force protection

  • otpVerifyRateLimit/otpRequestRateLimit are skipped unless NODE_ENV==='production' (authRateLimit.ts:27).
  • Express has no app.set('trust proxy', 1). Behind nginx every request comes from 127.0.0.1, so 10 failed verifies in 15 minutes lock out all users worldwide. express-rate-limit v8 also logs an X-Forwarded-For validation error.
  • Game endpoints, join-link polling aside, have no rate limit at all.
  • Admin: throttle:100,0.2 allows 100 requests per 12 seconds per IP (routes/admin.php:30), and the captcha rule is commented out (HomeController.php:50). There is no lockout and no 2FA.
Fix
Set trust proxy to the exact hop count. Key OTP limits by email+IP. Add a per-account counter in the DB. Admin: throttle:5,1 on POST /login, restore captcha after 3 failures, and consider TOTP for usertype 0/1.

Sessions and tokens: admin login regenerates the session (Laravel SessionGuard::login), deletes other sessions and checks role status. Good. Organizer JWTs last 24 h, are stored in localStorage (frontend/src/api/client.ts) and cannot be revoked server-side except by suspending the account (authMiddleware.ts:63). jwt.verify has no algorithms pin; jsonwebtoken v9 rejects none, but pin ['HS256'] anyway. Password reset: there is no admin password-reset flow (only change-password while logged in), so no reset-token risk exists.

5. Authorization & IDOR (API + sockets)

C4 Players have no credential: the known game-summary IDOR is systemic

Verified as reported. GET /v1/participant/game-summary/:group_id?participant_id=N (participantController.ts:250-259) passes the query value straight into buildGameSummaryPayload, which returns that player's private briefing: role_subtitle/objective, "You are the one who did it" for the culprit, and the role icon (gameSummaryService.ts:328-433). Participant ids are sequential and shown in the lobby payload.

The same pattern applies everywhere:

  • /v1/participant/lobby/:group_id?participant_id=
  • every /v1/game/* POST (ask-question, answer-question, start/vote/end-lie-detector, use-passcard, submit-accusation, reopen-case-summary), which all take participant_id from the body
  • /v1/game/state/:group_id and /lie-detector/:round_id/tally
  • /v1/results/:group_id[/pdf]
  • all Cook & Create round endpoints (routes/cookandcreate/index.ts:13-166)

A player can answer, vote or accuse on behalf of others and see the impostor bias card (cookandcreate/game.tsx:1275-1280). verifyParticipantOtp returns a 64-hex join_token (:136,207), but no route or socket handler ever checks it.

Fix
After OTP verification, issue a signed participant token (JWT with participant_id, group_id and booking_id, or the existing join_token looked up server-side). Add a participantAuth middleware to every game, Cook & Create, lobby and results route, and take participant_id only from the verified token, ignoring the body and query. Check that the session belongs to group_id. Do the same in Socket.IO via io.use() handshake auth. (A separate proposal already covers the game-summary endpoint; widen it to all of these routes.)

C5 Organizer → global content admin

/v1/cookandcreate/admin/templates (GET/POST), /admin/templates/:id and /admin/ingredients (GET/POST/DELETE) are guarded only by the organizer authMiddleware. The controller updates cc_game_templates and cc_ingredients by id with no ownership or role check (cookandcreateController.ts:1041,1120-1136). Organizer registration is self-service and, with C1, needs only an email address. A deleted ingredient breaks every Cook & Create session.

Fix
Content is already managed in the Laravel admin (admin/cook-and-create/*), so delete these Node routes. If they're needed, protect them with a separate admin JWT audience, not the organizer token.

C6 Socket.IO has no authentication

join_organizer_dashboard {bookingId} joins organizer_${bookingId} and immediately emits buildEventStats, which includes participant name and email (socketHandler.ts:207-219, eventStatsService.ts:24-45). It then streams every join notification. leave_game_group {groupId, participantId} sets any player offline (:231-239), and join_lobby/join_cc_instance let anyone subscribe to any room's live game events. Socket CORS doesn't help: CORS only binds browsers.

Fix
Add io.use() middleware that verifies an organizer JWT or participant token. Allow join_organizer_dashboard only when organizer_bookings.organizer_id matches, and the group rooms only for the token's own group. Derive participantId from the token.

H1 Developer endpoint in production

router.post('/dev/advance/:group_id', devAdvance) (gameRoutes.ts:16) has no auth. Its own comment says "Remove the button that calls this before production" (gameEngineController.ts:308). The frontend still references it (participant.service.ts:106, api/config.ts:32).

Fix
Register the route only when NODE_ENV!=='production', and remove the UI button.

H2 · H3 · H5 Booking and checkout endpoints

  • H2 GET /v1/organizer/booking/:booking_id has no auth and returns organizer_email, company_name and invitation_link (organizerController.ts:340-377). Iterating ids yields every customer's email and a working join link for every event.
  • H3 POST /create-booking trusts organizer_id from the body (:283-338), so anyone can create bookings for any verified organizer. POST /complete-booking (:396) has no auth: anyone can attach their own GST/billing data to someone else's pending booking. With payment_method:'cod', activateBooking runs immediately and returns the invitation link (:553-567), so service is delivered unpaid whenever COD is enabled in settings.
  • H5 GET /event-stats/:booking_id uses authMiddleware but never checks ownership (:217-226). Compare notificationController.ts:16, which calls assertOrganizerBooking; that is the pattern to copy.
Fix
Require a token on all three. For first-time registrants, return a short-lived JWT from verify-otp instead of only organizer_id. Take organizer_id from req.user.id, and call assertOrganizerBooking(booking_id, req.user.id) in getBookingDetails, completeBooking and getEventStats. Remove invitation_link from the booking-details response until payment.

Endpoints that are correctly scoped: /dashboard, /profile, /profile/billing, /notifications/*, /invoices* (invoiceController.ts:14), /update-session, /results/cook-and-create/:id/pdf and /account/delete all derive the organizer from the JWT. /payment/verify relies on the Razorpay HMAC and tightens ownership when a token is present.

6. Admin panel audit

Routing and authentication. All admin routes except login and captcha sit in the auth:admin group (routes/admin.php:40-194), and the web middleware provides CSRF. Spot-checks returned the login redirect without a session. The login only accepts usertype 0/1/2 (HomeController.php:68), so a regular user (usertype 3) cannot log in. A direct HTTP request from an anonymous visitor cannot reach protected pages. The weakness is between admin roles.

H4 Role-based access control is mostly decorative

MenuPermission::checkRoutePermissions() lets usertype 0/1 through and checks roles.permissions for anyone else. Checks per controller (calls / public methods):

  • Users 9/8, EmailTemplate 10/9, CMS 9/10 (but checkPermission() returns true, CmsPageController.php:337-342), Role 8/11, Admin 7/11, SubAdmin 4/11, DatabaseExport 1/1.
  • Zero checks in Settings (including payment keys, OTP, email and invoice settings), Payments (including mark-paid), Organizers, Activities and Games, Music, Blogs, FAQs, Packages, Cook & Create and API logs.

Concrete escalation paths for any sub-admin (usertype 2):

  • POST users-permissions/admin/status-change {id:<super admin id>, status:inactive} deactivates the super admin. It takes a raw id with no permission or usertype filter (AdminController.php:261-285).
  • PUT users-permissions/admin/{encrypted id} updates any user row, including usertype 0/1, and sets email, password and role_id (:224-258). The encrypted ids can be forged with the leaked APP_KEY (C3).
  • POST users-permissions/admin creates an admin with any role_id, including 1 (Super Admin). There is no permission check and role_id is only required (:142-172).
  • POST role/rolePermissionSave grants every permission to any role; its checks are commented out (RoleController.php:296-322, see also :114,128,176,202).

Current state: the dev DB has only usertype 0/1 accounts and menu_permissions is empty, so this is latent. It becomes Critical the day a sub-admin is created.

Fix
Add a route middleware (admin.permission) that runs checkRoutePermissions($request->route()->getName()) on the whole protected group, and seed menu_permissions for every named route. In AdminController, scope all writes to usertype='2', validate role_id with Rule::in(allowed roles) excluding 1/2, and forbid editing yourself or a higher role. Uncomment and fix the Role checks.

H6 Arbitrary file read via showImage

Route::get('showImage/{a}/{b?}/{c?}/{d?}/{e?}') builds "/$a/$b/…" and calls file_get_contents(public_path($filename)) after only file_exists and a non-empty extension (HomeController.php:269-298). A segment of .. is a valid route parameter, so showImage/../.env-style paths escape public/. Whether the web server normalises .. first varies (curl --path-as-is, encoded %2e%2e). This was not exercised because it needs an admin session; rated on the code alone.

Fix
Remove the route if unused (grep finds no view using it). Otherwise realpath() the result, require it to start with realpath(public_path('storage')), and allow only image extensions.
