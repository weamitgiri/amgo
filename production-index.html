Laravel admin and backend

  • Routing. bootstrap/app.php loads routes/web.php, routes/admin.php (prefix admin) and routes/api.php (prefix api). The admin group uses auth:admin plus throttle:100,0.2.
  • RBAC. MenuPermission::checkRoutePermissions() is called only in AdminController, RoleController, SubAdminController and UsersController, and DatabaseExportController has its own check. The other 20 admin controllers (settings, organizers, payments, API logs, CMS, blogs, games, music, Cook & Create) have no permission check, so every logged-in admin-guard user (usertype 0, 1 or 2) can reach them. See ZV-011.
  • CSRF. No validateCsrfTokens(except: ...) exclusions were found, so the default web-group CSRF protection applies to admin POST routes. PASS on code review.
  • Mass assignment. No model uses $guarded = []. User has a broad $fillable that includes usertype and role_id. No direct $request->all() into User::create was traced in this audit (not exhaustively verified).
  • Uploads. MIME and size are validated, but stored names reuse the client-supplied extension (ZV-018). SVG is allowed for the profile image (ZV-019).
  • Session. Auth::guard('admin')->login() migrates the session ID through Laravel's SessionGuard, so there is no session-fixation finding. Logout invalidates and regenerates the session.
  • Debug config. The dev .env has APP_ENV=local, APP_DEBUG=true and SESSION_SECURE_COOKIE=false. The production values could not be checked (BLOCKED by the rule not to touch live).
  • Legacy API. /api/v1/auth/* and /api/v1/game-join/* are still routed and use a fixed OTP (ZV-005).
  • Exception handler. Contains leftover echo ...; die branches and a reference to a missing view front.front_warning. An unauthenticated /admin request returns HTTP 500 (ZV-022, ZV-027).

Frontend (TanStack Start React)

  • HTML sinks. 11 dangerouslySetInnerHTML uses: routes/game.tsx (3), join.$linkToken.tsx (3), policy.$slug.tsx, index.tsx, cookandcreate/game.tsx, RoleRevealModal.tsx and summary.tsx, plus the shadcn chart style tag. Every source traced is admin-authored rich text. None was traced to participant input. No sanitizer (such as DOMPurify) is used (ZV-020).
  • Token storage. The organizer JWT is kept in localStorage (lib/auth.ts:7). The participant join token is in sessionStorage with a localStorage browser lock. Any script injected through the sinks above could read the JWT (ZV-034).
  • Protected routes. Client-side guards exist (middleware/routes.ts, plus beforeLoad in the dashboard, groups, participants, payments, profile, notifications and hr-results routes). The real enforcement point is the API.
  • API URLs. Production builds fall back to http://localhost:6001 and http://localhost/p/storage when the Vite environment variables are missing (ZV-031).
  • Dev OTP toast. join.$linkToken.tsx:262 shows dev_otp only when import.meta.env.DEV is true. Correct.
  • SEO. src/seo/homeSeo.ts sets the title, description, canonical, robots, Open Graph, Twitter and JSON-LD for the homepage. PASS on code review. There is no frontend/public directory, so there is no robots.txt or sitemap.xml (ZV-033).
  • Type and lint health. tsc --noEmit reports 23 errors in 11 files. ESLint reports 3480 errors, 3443 of them prettier formatting (ZV-028).

Node / Express API

Architecture map

  • Process. One Express server (src/server.ts) with Socket.IO on the same HTTP server. It runs an in-process timer loop (timerService, setInterval) and the retention sweep. There is no Redis adapter, and the code warns that it must run as a single instance.
  • Organizer auth. Email OTP issues an HS256 JWT valid for 24h (organizerController.ts:145-154). authMiddleware re-checks organizer status on every request. There is no server-side revocation.
  • Participant auth. /v1/participant/join (booking_id, name, email) sends an OTP. /verify-otp returns a 64-hex join_token. participantAuth resolves the caller from X-Participant-Token and rejects a mismatched participant_id or route group_id.
  • Payments. Razorpay order creation uses a server-side amount from the package price (paymentService.ts:234). Checkout verification uses an HMAC with timingSafeEqual. The webhook verifies its signature over the raw body (razorpayWebhookController.ts:61). PASS on code review.
  • PDFs. Results PDFs (MQ per group, MQ per session, Cook & Create awards) and the GST invoice are served with res.download. There is no express.static exposure of the storage folder.
  • Retention. retentionService.ts:149 purges groups with status completed or incomplete once retention_purge_at has passed. It nulls participant name, email and OTP, and deletes game rows.

MySQL (dev database, read-only)

  • 75 tables, all InnoDB, all with a primary key, and 48 foreign-key constraints.
  • Unique keys present: organizers.email, users.email, users.username, organizer_bookings.invitation_link, game_participants.join_token, payments.gateway_order_id, payments.gateway_payment_id, votes(reference_id, reference_type, voter_id) and cc_ratings(voting_participant_id, rated_group_id).
  • Unique keys missing where the code assumes one row: game_participants(booking_id, email), participant_sessions(group_id, participant_id) and organizer_billings(booking_id). There are 0 duplicates today (ZV-023).
  • Indexes on hot lookup columns are present: game_participants.booking_id, participant_sessions.group_id and participant_id, timers(group_id, is_active, expires_at), questions.group_id, votes.group_id and payments.booking_id.
  • Types: payments.amount is DECIMAL(12,2) NOT NULL (good). game_participants.email is nullable by design (retention nulls it). organizer_bookings.invitation_link is nullable.
  • PII retention: 163 participant rows still hold an email. 133 of them belong to bookings scheduled more than 7 days ago whose groups are still active (71) or waiting (62), plus 1 with no group. The sweep never selects those groups (ZV-015). 23 groups keep a Cook & Create awards PDF path permanently (ZV-024).
  • Invoice settings: invoice_seller_gstin, address, city, state and state code are absent from settings, so invoices fall back to "PROVISIONAL RECEIPT" (ZV-012b).
  • DB account: both the Laravel and Node dev configs connect as the MySQL root user (ZV-025).
  • Unbounded queries (from code): buildEventStats returns every participant of a booking. This is bounded by the package size, not paginated. Admin lists use pagination.

Performance and reliability (code review only, not measured)

  • Single instance only. Socket rooms, presence and the timer loop live in process memory (server.ts comment, timerService.ts:32,51). The API cannot scale horizontally or survive a restart mid-game without the timer recovery logic. Run pm2 in fork mode with -i 1.
  • DB pool. connectionLimit defaults to 10 with queueLimit: 0 (unbounded queue) in config/db.ts:45-46. Under a burst, requests queue without a limit instead of failing fast.
  • Per-request schema checks. authMiddleware calls ensureOrganizerStatusColumns() on every authenticated request. If that is not memoised, it adds a query per request (not measured).
  • Logging. morgan('dev') runs in every environment (server.ts:83). There is no log rotation config in the repo for apis/logs.
  • PDF generation runs in the request or timer path with pdfkit, synchronously in the API process. Large groups could block the event loop briefly (not measured).
  • Stale dist. The committed apis/dist is stale, and production runs dist/. Every deploy must rebuild (see the deploy note: three separate builds).
  • Rate limiter keyed on the proxy IP behind nginx could throttle all users together (ZV-013).
